# 验证报告：分段感知流水线

> 验证环境：**CPU only**（本机无 CUDA 显卡），因此用极小尺寸验证**逻辑正确性**，
> 不验证速度与画质。真实效果需在有 N 卡的机器上测。

---

## 一、验证素材

程序合成的 3 镜头测试视频（`_test/tiny_3shots.mp4`）：

| 项 | 值 |
|---|---|
| 分辨率 | 64×64（BasicVSR++ 要求 ≥64，取最小值让 CPU 能跑） |
| 帧数 | 30 帧 @10fps = 3.0 秒 |
| 内容 | 镜头1 红、镜头2 绿、镜头3 蓝，每镜头 10 帧，各含一个移动白块（让 RIFE 有运动可插） |
| **真实切点** | **第 10 帧、第 20 帧** |

**分段结果**（OmniShotCut）：切点 `[10, 20]`，与真实完全一致 ✓

## 二、三个模式的验证结果

| 模式 | 分辨率 | 帧数 | 帧数守恒 | 切点处理 |
|---|---|---|---|---|
| **超分** | 64×64 → **256×256** | 30 → **30** | ✓ | 传播在切点重置 |
| **插帧** | 64×64 → 64×64 | 30 → **60** | ✓ | 跨切点帧对跳过 |
| **超分+插帧** | 64×64 → **256×256** | 30 → **60** | ✓ | 两者都用 |

## 三、关键验证点

### 3.1 插帧：切点处用重复帧，不产生鬼影 ✓

**分段感知**（`--mode fi`）：

| 输出帧 | 内容 |
|---|---|
| `out[18]` | 源帧 9（镜头1末帧，红）R=250 G=15 |
| `out[19]` | **源帧 9 的副本** R=250 G=15 ← 差异 **0.00** |
| `out[20]` | 源帧 10（镜头2首帧，绿）R=15 G=252 |

**对照组**（`--mode fi --no-shot-aware`）：

| 输出帧 | 内容 |
|---|---|
| `out[18]` | 源帧 9（红）R=250 G=15 |
| `out[19]` | **RIFE 插出的混合帧** R=49 **G=213** ← 红绿叠加 = **鬼影** ✗ |
| `out[20]` | 源帧 10（绿）R=15 G=252 |

**结论**：分段感知把「红绿混合的鬼影帧」替换成了「前一帧的干净副本」。

### 3.2 超分：分段计划在切点强制断开 ✓

**分段感知** `plan_chunks(30, cuts=[10,20], chunk=8, overlap=2)`：

```
read=(0, 8)   valid=(0, 8)
read=(6, 10)  valid=(8, 10)
read=(10,18)  valid=(10,18)   ← 从切点 10 开始，不取上一镜头的上下文
read=(16,20)  valid=(18,20)
read=(20,28)  valid=(20,28)   ← 从切点 20 开始
read=(26,30)  valid=(28,30)
```

**对照组** `plan_chunks_naive`：

```
read=(0, 8)   valid=(0, 8)
read=(6, 16)  valid=(8, 16)   ← ⚠️ 上下文跨越了切点 10
read=(14,24)  valid=(16,24)   ← ⚠️ 上下文跨越了切点 20
read=(22,30)  valid=(24,30)
```

**结论**：分段感知的每一段都**不从别的镜头借上下文**，BasicVSR++ 的双向时序传播
在切点处自然重置；对照组的 chunk 会把两个镜头的内容混在一起传播。

### 3.3 超分输出无跨镜头串色 ✓

输出颜色序列（源：红×10 → 绿×10 → 蓝×10）：

```
红 红 红 红 红 红 红 红 红 红 绿 绿 绿 绿 绿 绿 绿 绿 绿 绿 蓝 蓝 蓝 蓝 蓝 蓝 蓝 蓝 蓝 蓝
```

切点处像素值：
- 帧 9：R=250 G=15 B=15（纯红）
- 帧 10：R=15 **G=253** B=15（纯绿）
- 帧 19：R=15 G=253 B=15（纯绿）
- 帧 20：R=15 G=15 **B=246**（纯蓝）

**切点两侧干净突变，没有拖影或串色。**

### 3.4 帧数严格守恒 ✓

| 模式 | 公式 | 实测 |
|---|---|---|
| 超分 | N | 30 ✓ |
| 插帧 | 2N | 60 ✓ |
| 超分+插帧 | 2N | 60 ✓ |

`shotaware` 的自测还覆盖了极端情况：

```
n=1/2/5/100 各种切点组合下 输出帧数恒为 2N ✓
```

（切点数量不影响输出帧数——跨切点的对用重复帧补回，不会少帧。）

## 四、过程中发现并修复的 3 个 bug

### Bug 1：PATH 上有个 0 字节的 `ffmpeg.exe`

**现象**：`OSError: [WinError 193] %1 不是有效的 Win32 应用程序`

**根因**：系统 PATH 上有 `C:\Users\10415\AppData\Local\Microsoft\WinGet\Links\ffmpeg.exe`
——一个 **0 字节**的坏 WinGet shim。而 `bootstrap.ensure_ffmpeg()` 原来的逻辑是：

```python
if shutil.which("ffmpeg"):     # ← shutil.which 只看"文件存在且可执行"，
    return shutil.which("ffmpeg")  #    不验证它是不是有效的 PE 文件
```

于是它返回了这个坏文件，项目自带的正常 ffmpeg 永远没机会上场。

**修复**：改成「**优先用项目自带的，且必须实际跑一次 `ffmpeg -version` 验证**」；
系统 PATH 上的候选也要通过同样的验证才采用。

### Bug 2：主循环消费掉结束哨兵后永久阻塞

**现象**：处理完最后一批后进程再也不动（跑满 5 分钟超时）。

**根因**：reader 线程结束时往队列里投一个 `None` 哨兵。主循环的内层循环
`while len(batch) < micro_batch` 读到哨兵就 `break`，处理完这批之后，
**外层循环又去 `qin.get()` —— 此时 reader 已退出，队列也空了，永久阻塞。**

**修复**：增加 `reader_done` 事件；`get` 改成带 0.5s 超时，
超时后检查「reader 已结束 **且** 队列已空」才真正退出。

### Bug 3：`inference_mode` 外做原地操作 + 切错张量维度

**现象**：
```
RuntimeError: Inplace update to inference tensor outside InferenceMode is not allowed.
RuntimeError: permute: input.dim() = 5 is not equal to len(dims) = 4
```

**根因**：
1. 模型前向产出的张量是「推理张量」，出了 `inference_mode` 再做 `clamp_()` / `mul_()`
   这类**原地**操作会被 PyTorch 拒绝（原项目的 `vsr_engine.py` 注释里提过这点，我漏了）
2. BasicVSR++ 的输出是 **5 维** `(1, T, C, H, W)`，我写成了 `y[ctx:...]`
   ——那是在切 **batch 维**，不是时间维

**修复**：整个 `upscale` 包在 `inference_mode` 里；取输出改成 `y[0, ctx:...]`。

| 项 | 为什么没验 |

| fp16 + fp32 warp 的效果 | 无 CUDA |

切点是否对齐、跨切点是否跳过、帧数是否守恒、有没有明显的串色/鬼影。
这些都通过了。**画质与性能需要在有 N 卡的机器上另行验证。**
