## 1. RIFE 的 TensorRT 引擎精度不达标 —— 明确的性能提升点

### 现状

- RIFE 的 TRT 引擎已构建并随发布分发（`rife_3360x1920_warp+resize.trt`，337.7 MB，
  变体含义：GridSample / Resize 留在 fp32 的「手术版」）。
- **真实素材实测**（liuqiang.mp4 480×836 → VSR ×4 → 1920×3344，对 PyTorch fp32 真值）：

  | 实现 | ms/对 | PSNR | 最大差 | >2/255 | 最大连通块 |
  | --- | --- | --- | --- | --- | --- |
  | **PyTorch fp16（当前默认）** | 131.2 | 61.75 dB | **1.0** | **0.000%** | **0** |
  | TRT-fp16 | 55.3 | 46.35 dB | 57.0 | 8.569% | 114183 |
  | **TRT-warp+resize（最优变体）** | **56.4** | 55.14 dB | **32.0** | 0.300% | **2145** |

- **结论：精度不达标** —— 即使是做过算子手术的最优变体，最大差仍有 **32/255**，
  且成片存在 **2145 像素的连通块状伪影**，肉眼可见。
- 因此**当前流水线默认使用 PyTorch 后端**（`rife_backend="torch"`：fp16 + warp 强制 fp32，
  精度对齐 fp32 —— 最大差 1/255、50% 像素与 fp32 逐位相同）。
  这是精度优先的保守选择，**代价是插帧段损失约 2 倍速度**。

### 为什么值得修（性能空间）

- TRT 版比 torch 后端快 **~1.9–2.3×**（视分辨率与引擎变体），是当前流水线里
  最直接、收益最大的提速点。若能把精度修到达标（目标：最大差 ≤2/255、无连通块伪影），
  插帧段耗时可直接减半。

### 已知的根因与已做工作

1. **TensorRT 硬限制**：TRT 会**静默忽略** ONNX GridSample 的 `padding_mode` 属性
   （只支持 zeros），改属性无效（实测一个数都不变）。已用「算子手术」绕开：
   把 warp / resize 拆成 TRT 支持的等价形式、并留在 fp32。
2. 已实测的变体：fp16 / strongmix / warp-only / warp+resize —— 最优为 warp+resize，
   但仍差 **30 个灰阶**（32/255）。
3. 精度测试教训：必须用**真实视频帧**（合成帧接缝硬跳变会放大误差，早期测出的
   232/183 最大差不可信；真实素材下重测为 32.0）。

### 建议下一步

- [ ] **逐层二分**：同一输入下对比 TRT 与 PyTorch 的中间特征，定位误差首次放大的层
- [ ] 尝试 `STRONGLY_TYPED` 网络 + 敏感层强制 fp32（混合精度重建引擎）
- [ ] 复查剩余算子（除 GridSample 外）是否还有被 TRT 改写/近似的行为
- [ ] RIFE 是浅层卷积网络，理论上 fp16 不应产生 32/255 的差 ——
      怀疑还有类似 padding_mode 的「静默行为差异」尚未找到

## 2. VSR 的 TensorRT 引擎对输入分辨率的要求 —— 待进一步确认

### 现状（代码行为）

- 引擎是**定形编译**的：输入形状在构建时写死，`SrTrtEngine` 按
  `vsr_{mode}_t{t}_{h}x{w}_x4.trt` 命名约定**精确匹配查找**（`pipeline/sr_trt.py::find_engine`），
  找不到对应分辨率的引擎就直接报错并给出构建/下载指引。
- 当前分发的两个引擎形状均为 **输入 836(H)×480(W)**（即 480×836 视频）@ ×4：
  - `vsr_tf32_t8_836x480_x4.trt`（134.5 MB，TF32，78.54 dB / 1.69×）
  - `vsr_tf32_t2_836x480_x4.trt`（155 MB，TF32，80.28 dB / 1.86×）
- **其他输入分辨率下的端到端表现尚未系统验证** —— 目前只有 836×480 一条实测数据。

### 待确认的问题清单

- [ ] **补边复用**：能否把任意分辨率补边到 836×480 推理、再裁回目标尺寸？
      注意 BasicVSR++ 是**全序列时序传播**，补进去的帧/区域会参与对齐与传播
      （已有前车之鉴：尾部补 2 帧会让**前面每一帧**都变化，最大差 27/255）——
      空间补边是否同理、影响多大，必须实测。
- [ ] **多引擎策略**：常用分辨率（720×1280、1080×1920、752×1336…）是否需要
      各自预编译引擎？单文件 135 MB+，走 GitHub Release 分发，体积成本需要权衡。
- [ ] **动态 shape（optimization profile）**：TensorRT 支持动态形状，但需要重建引擎
      并**重新做一遍精度验证**（当前 tf32 精度结论只对定形引擎成立）。
- [ ] **与 autoconfig 联动**：服务端目前按输出像素自动选后端（vsr/resr）；
      接入 TRT 后需要"按输入分辨率找引擎、找不到就降级 torch"的完整策略。

### 影响

不解决分辨率适配问题，TRT 的 1.69× 提速只能在单一尺寸上享受，无法作为通用后端。

## 3. 云服务器带宽瓶颈 —— 公有入口传大文件太慢

### 实测数据（2026-10-16，经 FRP 隧道 TCP 代理）

| 指标 | 实测值 |
| --- | --- |
| 上传 | **~72 KB/s**（15 MB 文件耗时 214 s） |
| 下载 | **~88 KB/s**（1 MB 限速测速） |
| RTT | ~111 ms |

### 影响

- 通过公网入口提交大文件极慢：**100 MB 视频 ≈ 24 分钟**；
- 结果下载同样受限（35 MB 产物约需 7 分钟）；
- 只适合小文件、低频率的演示/测试场景。

### 当前缓解方案

- 小文件（几十 MB 以内）可直接走公网入口；
- **大文件用局域网地址或本机提交**，或放到服务端 `webapp/data/inbox/`，
  用 `POST /api/jobs/json` 的 path 模式提交（完全不走网络，秒级受理）；
- 结果文件也可在服务端就地回拷，避免下载。

### 可能的改进方向

- [ ] 升级云服务器带宽 / 更换接入线路
- [ ] 更换或自建中转节点（就近接入）
- [ ] 大文件走对象存储或断点续传方案，不走同步隧道
